# CRUDFlow Compiler 기획 초안

> **CRUDFlow Compiler — 요구사항을 Netlify·Supabase 기반 CRUD 워크플로우로 변환하는 설계 체계**

## 1. 프로젝트 개요

CRUDFlow Compiler는 사용자가 만들고 싶은 업무 기능을 설명하면, 이를 Netlify와 Supabase 기반의 Create·Read·Update·Delete 구축 절차로 변환하는 에이젼트 워크플로우다.

사용자가 코드를 직접 작성하지 못하더라도 다음을 결정할 수 있도록 돕는다.

- 어떤 데이터를 입력·조회·수정·삭제할 것인가
- 프론트엔드, Netlify Function, Supabase가 각각 무엇을 담당하는가
- 어느 순서로 구현하고 검증해야 하는가
- 실패했을 때 어디부터 확인하고 복구해야 하는가
- 어떤 상황에서 사용자에게 판단을 요청해야 하는가

단순 코드 생성기가 아니라 질문, 설계, 구현, 검증, 오류 복구와 운영 문서화를 포함하는 반자동 구축 체계를 목표로 한다.

## 2. 탄생 배경

기존 `Netlify + Supabase + Slack 폼 구축 워크플로우`는 CRUD 중 Create를 구축하는 원형에 해당한다.

```text
폼 입력
→ 프론트 유효성 검사
→ Netlify Function 호출
→ 파일 업로드
→ Supabase INSERT
→ Slack 알림
→ 성공 화면 처리
```

이 원형에서 Slack처럼 특정 기능에만 필요한 단계를 분리하고, 쿼리와 화면 흐름을 변형하면 Read·Update·Delete 워크플로우로 확장할 수 있다.

```text
Create 원형
→ 공통 구조 추출
→ Read·Update·Delete 변형
→ 공통 질문과 검증 체계 통합
→ CRUDFlow Compiler
```

## 3. 핵심 목표

1. 자연어 요구사항을 실행 가능한 CRUD 설계로 변환한다.
2. 초보자도 한 단계씩 따라갈 수 있는 질문형 워크플로우를 제공한다.
3. 기능별로 프론트·서버·DB의 역할을 명확히 분리한다.
4. 샘플 기능부터 검증한 뒤 전체 기능으로 확장한다.
5. 오류 경험을 FAQ와 알려진 문제에 축적한다.
6. 다른 프로젝트에서도 재사용할 수 있는 템플릿과 체크리스트를 만든다.
7. AgentFlow Compiler 원칙에 따라 토큰·속도·오류 복구·사용자 판단 시점을 최적화한다.

## 4. 대상 사용자

- 코드를 직접 작성하기 어렵지만 업무 흐름을 설명할 수 있는 사용자
- 작은 관리자 도구, 문의 관리, 신청 목록, 콘텐츠 관리 기능이 필요한 사용자
- Netlify와 Supabase로 소규모 웹 서비스를 빠르게 구축하려는 사용자
- AI 에이젼트와 함께 반복 가능한 개발 절차를 만들고 싶은 사용자

## 5. 기본 기술 구조

```text
사용자 브라우저
├─ 입력 폼
├─ 목록·상세 화면
├─ 수정 화면
└─ 삭제 확인 UI
        ↓ HTTPS 요청
Netlify Functions
├─ 입력값 서버 검증
├─ 권한 확인
├─ Supabase 요청
├─ 오류 분류
└─ 응답 정규화
        ↓
Supabase
├─ Database
└─ Storage
```

기능에 따라 Slack, 이메일, 인증 같은 외부 기능을 선택 모듈로 연결한다. CRUD의 기본 흐름과 부가 기능을 섞지 않는다.

## 6. 네 가지 핵심 모듈

### 6.1 CreateFlow

목적: 사용자의 입력을 검증하고 새로운 데이터를 저장한다.

```text
입력
→ 프론트 검증
→ 서버 검증
→ 파일 업로드
→ DB INSERT
→ 선택 알림
→ 성공 처리
```

핵심 항목:

- 필드와 DB 컬럼 매핑
- 필수값 및 형식 검증
- 파일 확장자·용량·안전성 검사
- 중복 제출 방지
- DB 성공 전 성공 화면 금지
- Slack·이메일 등 알림 실패와 DB 실패 분리

### 6.2 ReadFlow

목적: Supabase 데이터를 조회해 목록과 상세 화면에 표시한다.

```text
페이지 접속
→ 로딩 상태
→ Netlify Function 호출
→ Supabase SELECT
→ 응답 정규화
→ 목록 또는 상세 출력
```

핵심 항목:

- 목록과 상세 조회 분리
- 로딩·빈 목록·조회 실패 상태
- 정렬과 필터
- 검색
- 페이지네이션
- 이미지와 첨부파일 출력
- 사용자에게 노출해도 되는 컬럼 선별

### 6.3 UpdateFlow

목적: 기존 데이터를 조회하고 변경된 값을 안전하게 저장한다.

```text
기존 데이터 조회
→ 수정 폼 채우기
→ 사용자 수정
→ 프론트·서버 검증
→ 파일 교체 또는 유지
→ DB UPDATE
→ 변경 결과 확인
```

핵심 항목:

- 수정 대상 식별자
- 수정 권한 확인
- 기존 값과 변경 값 구분
- 변경된 필드만 업데이트할지 전체 교체할지 결정
- 기존 파일 유지·교체·삭제 정책
- 동시 수정 충돌 방지
- 변경 이력 필요 여부

### 6.4 DeleteFlow

목적: 삭제 영향을 확인하고 데이터와 연결 파일을 안전하게 정리한다.

```text
삭제 요청
→ 사용자 재확인
→ 권한 확인
→ 연결 데이터와 파일 확인
→ Storage 정리
→ DB DELETE 또는 소프트 삭제
→ 결과 확인
```

핵심 항목:

- 영구 삭제와 소프트 삭제 선택
- 삭제 전 재확인
- 삭제 권한 검사
- 연결된 Storage 파일 정리
- 일부 삭제 실패 시 복구
- 감사 로그와 복구 가능성

## 7. 공통 모듈

CRUD마다 반복되는 규칙은 공통 모듈로 관리한다.

```text
common/
├─ 프로젝트 정의
├─ 데이터 스키마
├─ 인증과 권한
├─ 입력값 검증
├─ 오류와 상태
├─ 파일 처리
├─ 로그와 추적 ID
├─ 배포와 검증
└─ 보안 체크리스트
```

### 공통 원칙

1. 프론트 검증을 신뢰하지 않고 서버에서 다시 검증한다.
2. 서비스 키와 Webhook URL은 환경변수로만 관리한다.
3. 서버는 일관된 성공·실패 JSON 형식을 반환한다.
4. 사용자 메시지와 서버 상세 오류를 분리한다.
5. 중요한 요청에는 추적 ID를 부여한다.
6. 데이터 변경 작업은 권한과 대상 존재 여부를 확인한다.
7. 성공이 확인되기 전에 성공 UI나 리디렉션을 실행하지 않는다.
8. 정식 배포는 사용자 확인 후에만 실행한다.

## 8. 사용자가 처음에 답할 질문

CRUDFlow Compiler는 구현 전에 다음을 질문한다.

### 프로젝트 목적

- 무엇을 관리하는 기능인가?
- 누가 사용하는가?
- 공개 페이지인가, 관리자 전용인가?
- MVP인가, 실제 운영용인가?

### 데이터

- 어떤 정보를 저장할 것인가?
- 필수값과 선택값은 무엇인가?
- 파일이나 이미지가 있는가?
- 개인정보가 포함되는가?

### CRUD 범위

- 등록이 필요한가?
- 목록과 상세 조회가 필요한가?
- 수정이 필요한가?
- 삭제가 필요한가?
- 검색·필터·정렬·페이지네이션이 필요한가?

### 권한

- 누구나 등록할 수 있는가?
- 누가 목록을 볼 수 있는가?
- 누가 수정·삭제할 수 있는가?
- 로그인이 필요한가?

### 완료 후 동작

- 성공 시 같은 화면에 메시지를 표시할 것인가?
- 다른 페이지로 이동할 것인가?
- Slack이나 이메일 알림이 필요한가?

사용자가 판단하기 어렵다면 에이젼트가 가장 단순하고 안전한 MVP 기본값을 추천한다.

## 10. MVP 범위

첫 MVP는 전체 CRUD를 한 번에 만들지 않는다. 기존 CreateFlow 다음으로 ReadFlow를 완성한다.

### MVP 목표

```text
Supabase 테이블 하나
→ Netlify Function으로 SELECT
→ HTML 목록 출력
→ 로딩·빈 목록·조회 실패 처리
```

### MVP에 포함

- 기존 테이블 선택
- 출력할 컬럼 선택
- Function의 SELECT 요청
- 최신순 또는 지정 기준 정렬
- HTML 목록 렌더링
- 로딩 상태
- 데이터 없음 상태
- 조회 실패 상태
- draft 배포 검증

### MVP에서 제외

- 사용자 로그인
- 복잡한 권한 체계
- 실시간 구독
- 고급 검색
- 대량 데이터 최적화
- Update와 Delete

MVP가 안정적으로 동작한 뒤 상세 조회, 검색, 페이지네이션 순서로 확장한다.

## 11. 개발 로드맵

### 1단계: CreateFlow 원형 정리

- 기존 폼 구축 문서 분석
- 공통 규칙과 Create 전용 규칙 분리
- Slack을 선택 모듈로 분리
- 누락된 보안·중복 제출·고아 파일 규칙 보완

### 2단계: ReadFlow MVP

- SELECT Function
- 목록 UI
- 로딩·빈 목록·오류 상태
- 샘플 데이터 검증
- draft 배포

### 3단계: ReadFlow 확장

- 상세 페이지
- 검색·필터·정렬
- 페이지네이션
- 이미지·첨부파일 출력

### 4단계: UpdateFlow

- 기존 값 불러오기

- 권한 및 서버 검증
- 파일 유지·교체·삭제

### 5단계: DeleteFlow

- 삭제 확인 UI

### 6단계: Compiler 통합

- 프로젝트 질문 템플릿

- 프로젝트별 체크리스트 생성
- 알려진 문제와 사용자 결정 학습

## 12. AgentFlow Compiler 적용 원칙

CRUDFlow Compiler는 AgentFlow Compiler의 하위 실전 모듈로 운영한다.

```text
자연어 요구사항
→ 프로젝트 목적과 성공 조건 분석
→ 필요한 CRUD 모듈 선택
→ 프론트·서버·DB 역할 분리
→ 작은 기능부터 구현·검증
→ 오류와 사용자 결정을 문서화
→ 다음 단계에 자동 반영
```

실행 중 다음을 지킨다.

- 긴 코드와 로그를 불필요하게 대화에 반복 출력하지 않는다.
- 상태와 결정 사항은 `project-overview.md`에 저장한다.
- 구현 단계마다 완료 조건을 검증한다.
- 신규 요구사항이 나와도 현재 검증 단계를 무시하고 건너뛰지 않는다.
- 모호한 판단은 사용자에게 영향과 추천안을 함께 제시한다.
- 오류를 해결하면 `KNOWN_ISSUES.md`와 기본 워크플로우를 갱신한다.

## 13. ReadFlow 시작 프롬프트

```text
기존 Netlify + Supabase 폼 구축 문서를 CreateFlow의 원형으로 분석해줘.

목표는 `CRUDFlow Compiler`를 만드는 것이다.
먼저 Slack 알림은 제외하고, Supabase 데이터를 조회하여 HTML 목록으로 출력하는 ReadFlow MVP를 설계해줘.

바로 구현하지 말고 먼저 다음을 제안해줘.

1. 기존 CreateFlow에서 재사용할 공통 단계
2. ReadFlow에서 새로 필요한 단계
3. 사용자에게 확인할 질문
4. 프론트·Netlify Function·Supabase의 역할
5. 로딩·빈 목록·조회 실패 상태
6. 샘플 검증 절차
7. 이후 상세·검색·수정·삭제로 확장할 구조

AgentFlow Compiler 원칙에 따라 도구 역할, 체크포인트, 오류 복구와 사용자 승인 지점을 포함해줘.

설계 승인 후 가장 작은 ReadFlow 샘플을 구현하고, 검증 결과를 문서와 project-overview.md에 반영해줘.
```

## 14. 성공 기준

CRUDFlow Compiler의 성공은 코드 생성량으로 판단하지 않는다.

- 비개발자가 질문에 답하며 CRUD 요구사항을 정리할 수 있는가?
- 에이젼트가 필요한 모듈과 구현 순서를 일관되게 결정하는가?
- 작은 샘플부터 단계적으로 검증하는가?
- 실패 지점과 복구 방법을 사용자가 이해할 수 있는가?
- 동일한 오류와 질문을 다음 프로젝트에서 반복하지 않는가?
- 생성된 기능이 실제 데이터와 파일을 안전하게 처리하는가?
- 다른 프로젝트에서도 워크플로우를 재사용할 수 있는가?

## 15. 다음 행동

1. 기존 폼 구축 문서를 `CreateFlow.md`의 원형으로 복사한다.
2. 공통 규칙과 Create 전용 규칙을 표시한다.
3. ReadFlow MVP용 실제 샘플 프로젝트 하나를 정한다.
4. 출력할 Supabase 테이블과 컬럼을 선택한다.
5. ReadFlow 시작 프롬프트로 설계를 시작한다.

첫 샘플 프로젝트는 데이터 구조가 단순하고 개인정보가 없는 목록이 좋다. 예를 들어 공지사항, 상품 목록, FAQ 또는 테스트 문의 목록을 사용할 수 있다.
