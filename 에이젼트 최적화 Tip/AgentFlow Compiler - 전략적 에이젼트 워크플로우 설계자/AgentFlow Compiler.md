# 에이젼트의 개념과 최적화 프롬프트

> **AgentFlow Compiler — 모호한 지시를 최적화된 에이전트 실행 흐름으로 변환하는 기능**

이 문서에서 설명하는 개념과 프롬프트 체계를 **AgentFlow Compiler**라고 부른다. 사용자의 목표 중심 지시를 분석하여 도구별 역할, 체크포인트, 묶음 처리, 오류 복구, 사용자 판단 시점과 검증 절차가 포함된 실행 가능한 워크플로우로 변환한다.

```text
모호한 사용자 지시
→ 목표와 판단 기준 분석
→ 도구별 역할 분리
→ 토큰·속도·복구 전략 설계
→ 검증 가능한 에이전트 실행 흐름
```

## 1. 에이젼트란 무엇인가

단순 챗봇은 보통 질문을 받고 답변을 생성한다.

```text
질문 → 답변
```

에이젼트는 사용자의 목표를 달성하기 위해 작업 환경을 확인하고, 적절한 도구를 선택해 실행하며, 결과를 검증하고 실패를 복구한다. 반복 작업 중 발견한 규칙과 사용자의 결정을 다음 작업에 반영해 실행 방식 자체도 개선한다.

```text
목표 이해
→ 환경과 기존 결과 확인
→ 작업 계획 및 도구 선택
→ 실행
→ 결과 검증
→ 오류 진단과 복구
→ 워크플로우 개선
→ 다음 작업에 반영
```

핵심은 단순히 도구를 사용하는 데 있지 않다. 목표를 기준으로 도구의 역할과 실행 순서를 설계하고, 문제가 발생했을 때 안전하게 복구하며, 같은 문제를 반복하지 않도록 작업 방식을 갱신하는 것이 에이젼트의 본질이다.

## 2. 실용적인 에이젼트 작업의 세 층

### 2.1 사용자: 목적과 판단 기준

사용자는 다음을 제공한다.

- 최종적으로 원하는 결과
- 반드시 지켜야 할 기준
- 애매한 상황에서의 판단
- 샘플 결과에 대한 승인 또는 수정 의견

사용자가 모든 기술적 실행 방법을 지정할 필요는 없다. 무엇이 올바른 결과인지 판단할 수 있는 기준을 주는 것이 더 중요하다.

### 2.2 에이젼트: 계획, 판단, 도구 조율

에이젼트는 다음을 담당한다.

- 입력 파일과 현재 상태 확인
- 작업을 단계와 묶음으로 분리
- 단계별로 가장 적합한 도구 선택
- 사용자 판단이 필요한 항목과 자동 처리 가능한 항목 구분
- 오류 원인 진단과 대체 경로 실행
- 결과 검증과 완료 보고
- 작업 중 배운 규칙을 명세와 워크플로우에 반영

### 2.3 스크립트와 도구: 반복적이고 결정적인 실행

스크립트와 전문 도구는 다음을 담당한다.

- 반복되는 데이터 변환
- 파일 생성과 다운로드
- CSV 병합과 정렬
- 형식 및 경로 검증
- 체크포인트 저장

모델이 반복 데이터를 대화에서 직접 다루는 대신, 결정적인 작업은 코드와 도구에 맡긴다. 에이젼트는 결과와 예외를 관리하고 사용자는 필요한 판단만 수행한다.

```text
사용자: 목적과 판단 기준
에이젼트: 계획·도구 선택·예외 처리·검증
스크립트와 도구: 반복적이고 결정적인 실행
```

## 3. 워크플로우 최적화가 중요한 이유

결과만 요청하면 에이젼트가 매번 많은 데이터를 대화로 가져오거나 동일한 작업을 반복할 수 있다. 먼저 실행 방식을 설계하고 한 묶음을 수행한 뒤 개선하면 다음 효과가 있다.

- 불필요한 대화 출력과 토큰 사용 감소
- 반복 작업의 실행 속도 향상
- 도구별 책임이 분리되어 오류 범위 축소
- 체크포인트를 이용한 빠른 재시작
- 사용자에게 필요한 판단만 선별해 질문
- 작업 과정에서 발견한 규칙의 지속적인 재사용

### 비효율적인 흐름

```text
브라우저에서 전체 페이지 읽기
→ DOM, 본문, 이미지 URL을 대화에 모두 출력
→ 모델이 파일을 하나씩 직접 작성
→ 중간 오류 발생 시 처음부터 다시 수집
```

### 최적화된 흐름

```text
브라우저는 동적 데이터 추출만 담당
→ 상세 결과는 로컬 체크포인트에 직접 저장
→ 파일 다운로드와 변환은 전용 도구 또는 스크립트가 담당
→ 검증 결과와 사용자 판단 항목만 대화에 보고
→ 오류가 발생하면 체크포인트부터 재개
```

## 4. 토큰 사용을 줄이는 실행 원칙

1. 전체 DOM, 긴 본문, 전체 HTML, 대량의 URL 목록을 대화에 출력하지 않는다.
2. 상세 추출 결과는 JSON 등 로컬 체크포인트에 저장한다.
3. 대화에는 처리 수, 성공, 경고, 실패와 검수 항목만 출력한다.
4. 반복 변환과 파일 생성은 로컬 스크립트에 맡긴다.
5. 같은 브라우저 탭과 실행 환경을 가능한 범위에서 재사용한다.
6. 작업을 적절한 묶음으로 나눠 묶음마다 체크포인트와 검증 결과를 남긴다.
7. 이미 완료된 항목은 다시 접속하거나 다운로드하지 않는다.
8. 토큰 절약을 이유로 검증, 오류 원문 또는 복구 정보를 버리지 않는다. 상세 정보는 대화가 아닌 로컬 로그에 보존한다.

토큰 최적화는 필요한 정보를 없애는 일이 아니다. 상세 정보가 저장되는 위치를 대화에서 체크포인트와 로그로 옮기는 일이다.

## 5. 사용자 판단이 필요한 상황의 처리

작업 중 처음 보는 필드, 불명확한 데이터 또는 스키마 변화가 발견돼도 현재 묶음 전체를 멈추지 않는다.

```text
신규 항목 발견
→ 원문을 체크포인트에 임시 보존
→ 현재 묶음은 끝까지 처리
→ 동일 항목을 묶어 사용자에게 한 번만 질문
→ 사용자 결정 반영
→ 명세·스크립트·기존 데이터 수정
→ 전체 재검증
```

질문에는 원문, 대표 값, 영향 범위와 추천 판단을 함께 제공한다.

```text
발견 순번: 31
원문 속성: 소재
원문 값: 폴리 100%
추천 매핑: attr_quality
영향 범위: 2개 상품
질문: 기존 컬럼에 매핑할까요, 별도 필드로 유지할까요?
```

사용자의 결정은 이번 데이터만 수정하는 것으로 끝내지 않는다. 다음 작업부터 자동 적용되도록 작업 명세, 파싱 규칙과 기존 파생 데이터를 함께 갱신한다.

## 6. 오류를 워크플로우 개선으로 연결하기

에이젼트는 오류를 단순히 재시도하는 데서 끝내지 않는다.

1. 실패한 단계와 도구를 분리한다.
2. 원본 오류 유형과 메시지를 보존한다.
3. 안전한 대체 방식을 시도한다.
4. 대체 방식이 성공하면 결과를 정상화한다.
5. 원인과 대응을 알려진 문제 문서에 기록한다.
6. 같은 문제가 다시 발생하지 않도록 기본 도구 또는 실행 순서를 수정한다.

예를 들어 페이지 파싱은 성공했지만 별도 다운로드 도구에서 TLS 오류가 발생했다면, 페이지나 이미지 자체의 실패로 오판하지 않는다. 다운로드 도구를 교체하고 동일 URL의 성공 여부를 검증한 뒤 기본 워크플로우를 수정한다.

## 7. 권장 묶음 처리 전략

반복 작업은 먼저 한 개의 샘플로 구조를 확인한 다음 10개 안팎의 묶음으로 처리하는 것이 안전하다.

```text
샘플 1개 처리 및 승인
→ 10개 묶음 실행
→ 체크포인트 저장
→ 결과와 신규 판단 항목 검수
→ 규칙 반영
→ 다음 묶음 실행
```

형식이 안정적이고 오류 복구가 검증된 경우에만 묶음 크기를 늘린다. 신규 필드가 발견돼도 묶음 처리는 계속하며, 묶음 종료 후 사용자 판단을 받는다. CAPTCHA, 로그인 제한, 페이지 구조 전체 변경처럼 정상 실행 자체가 불가능한 경우에만 중단한다.

## 8. 재사용 가능한 최적화 프롬프트

다음 프롬프트를 반복적인 데이터 수집, 파일 변환, 문서 정리 또는 웹 자동화 작업의 시작점으로 사용할 수 있다.

```text
이 작업의 최종 결과만 바로 만들지 말고, 먼저 샘플 1개를 기준으로 가장 효율적인 워크플로우와 사용할 도구의 역할을 설계해줘.

목표:
- [원하는 최종 결과]

입력:
- [입력 파일 또는 URL]

출력:
- [원하는 파일과 데이터 형식]

실행 원칙:
1. 브라우저, API, 로컬 스크립트 등 각 도구는 가장 잘하는 단계에만 사용해줘.
2. 전체 DOM, 긴 본문, HTML, 이미지 URL 목록 등 상세 데이터는 대화에 출력하지 말고 로컬 체크포인트에 저장해줘.
3. 대화에는 진행 건수, 성공·경고·실패와 내가 판단해야 할 항목만 요약해줘.
4. 반복적인 변환과 파일 생성은 재실행 가능한 스크립트로 처리해줘.
5. 완료된 항목을 식별하여 재실행 시 다시 수집하거나 다운로드하지 않게 해줘.
6. 작업을 적절한 묶음으로 처리하고 묶음마다 체크포인트와 검증 결과를 남겨줘.
7. 신규 필드나 애매한 데이터가 발견돼도 현재 묶음을 중단하지 말고 원문을 보존한 뒤 묶음 종료 후 한 번에 질문해줘.
8. 사용자 판단이 확정되면 현재 결과뿐 아니라 명세, 매핑 규칙, 스크립트와 기존 파생 데이터에도 반영해줘.
9. 오류가 발생하면 원본 오류를 로그에 보존하고 대체 방법으로 복구한 뒤, 재발 방지 규칙을 워크플로우와 알려진 문제 문서에 추가해줘.
10. 토큰 절약을 이유로 필수 검증이나 오류 기록을 생략하지 말아줘.

먼저 샘플 작업과 워크플로우를 보여주고, 승인 후 나머지 작업을 진행해줘.
```

## 9. 이미 시작한 작업을 최적화하는 프롬프트

작업이 이미 진행 중이라면 다음과 같이 요청할 수 있다.

```text
현재까지의 작업 방식과 생성된 결과를 분석해줘.

다음 관점에서 워크플로우를 개선해줘.
- 토큰 사용량
- 처리 속도
- 도구별 역할 분리
- 중간 실패 시 복구 가능성
- 재실행 시 중복 작업 방지
- 사용자에게 질문해야 하는 시점
- 결과 검증 자동화

개선된 흐름을 먼저 설명하고 작업 명세에 반영해줘. 기존 결과를 임의로 삭제하거나 덮어쓰지 말고, 샘플 묶음으로 검증한 뒤 나머지 작업에 적용해줘.
```

## 10. 완료 전 체크리스트

- 최종 목표와 산출물이 명확한가?
- 도구별 역할이 겹치지 않는가?
- 상세 데이터가 대화가 아닌 체크포인트에 저장되는가?
- 이미 완료된 작업을 재사용할 수 있는가?
- 오류 원문과 복구 결과가 기록되는가?
- 신규 규칙이 명세와 스크립트에 함께 반영되는가?
- 사용자 판단이 필요한 항목만 선별되어 있는가?
- 전체 행 수, 형식, 파일 경로와 상태가 검증됐는가?
- 최종 보고가 짧고 실행 가능한 정보로 구성됐는가?

## 11. 핵심 요약

좋은 에이젼트 작업은 모델이 모든 데이터를 직접 처리하는 방식이 아니다. 사용자는 목적과 판단 기준을 제공하고, 에이젼트는 계획과 도구를 조율하며, 스크립트는 반복 실행을 담당한다.

```text
좋은 결과
= 명확한 사용자 기준
+ 적절한 에이젼트 판단
+ 도구별 역할 분리
+ 체크포인트와 검증
+ 작업 과정에서의 지속적인 개선
```

결과물뿐 아니라 결과를 만드는 과정도 개선 대상으로 다룰 때, 토큰 사용량과 실행 시간은 줄고 정확성과 복구 가능성은 높아진다.
